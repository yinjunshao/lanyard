# Data Model

D1 schema from `migrations/0001`-`0024`. Conventions: ids are 10-character unguessable hex; timestamps are unix milliseconds.

## Identity
- `users` (**ai_search_ok** 1 or 0, default 1: people I've connected with may find me with AI search, F21 migration 0024; is_guest, recovery_email, email_domain, verified_student, has_passkey, over_18, plan, plan_until, notify_events)
- `sessions` (hashed token, expiry, user agent)
- `webauthn_credentials`, `webauthn_challenges`
- `rate_limits` (fixed-window counters)

## Profile and cards
- `profiles` (name, photo_key, **mode** `student`|`career` default `student`, **company** and **role** up to 80 characters each, uni, **institution_id** (F12, F29: a slug from the UK, US or world list, ids unique across the files; no migration for F29), course, year, headline, about, links JSON, tags JSON, projects JSON up to 3, is_public, show_age). **onboarding_step** (1 to 6, or NULL = not in the welcome steps) and **onboarding_max** (furthest step reached, default 0) are F14, migration 0022: NULL for every profile made before it and for anyone who has finished; a new card made through the steps starts at 2, and a guest's stub profile (made by connecting) starts at 1. Mode, company and role are F11, migration 0019. `uni`, `course` and `year` are kept in both modes; in Career mode `uni` reads "Studied at". Switching mode deletes nothing; only the chosen mode's fields are shown or searched. `institution_id` (F12, migration 0020) is a slug from `src/data/institutions-uk.json`, or NULL for typed or empty text; `uni` stays the display text (the official name for a listed institution, what was typed otherwise, up to 120 characters)
- `onboarding_stats` (day, step, reached, completed; primary key day + step): daily counts for the welcome-steps funnel, nothing about who (F14, migration 0022). Rows over 400 days old are purged
- `cards` (code, name, note, visible_links, tags, theme default|formal|night|host, strap_color, event_id, code_rotates_at)
- `card_codes` (current and grace codes with valid_until)

## Connections
- `connections` (user_a, user_b, event_id, selfie_key, consent_a, consent_b, **via**; unique per pair). `via` (F13, migration 0021) is how the first scan happened: `qr`, `code` or `link`. Rows made before 0021 are NULL, which means unknown and is shown as just "Connected"; nothing is guessed for them. It is written once, when the connection is made, and a later scan by either person never changes it. It is one value for the pair, so both people see the same wording. `event_id` has no foreign key: when an event is deleted or the host reset sets it to NULL, `via` stays and the event simply drops out of the wording
- `notes` (private per user), `messages` (thread), `blocks`, `reports`
- `consents` (record of who agreed to what, kept 6 years)

## Hosts and events
- Nothing is stored for shared ground (F16, no migration): `worker/inCommon.js` reads `profiles` (`mode`, `uni`, `institution_id`, `course`, `company`, `tags`), the card each person shared, `checkins`, `events`, `consents` and `blocks` on each request and returns text. There is no table, so nothing to export or delete ([[D026 Shared ground is worked out from what each person shows, and never stored]])
- `event_presence` (F17, migration 0023): `id` (opaque, unique), `event_id`, `user_id` (both cascade), `selfie_key` (R2, `presence/...`, private), `intro` (80), `looking_for` (120), `created_at`, `updated_at`; primary key (event_id, user_id). A row exists only while the person has presence on: turning it off deletes it. Deleted 48 hours after the event ends by `purgePresence` in `worker/purge.js`. `events.presence_used` is a counter of people who ever turned it on (the only thing a host sees). Consent scope `event_presence:<eventId>`.
- **Named attendance (F31, migration 0028).** `events.collect_attendance` (0 or 1, off), `collect_items` (JSON list, only `email` and `card`) and `collect_why` (the host's line, 10 to 200 characters, cleaned). `event_attendees(event_id, user_id, items, notice_version, created_at, updated_at, PRIMARY KEY (event_id, user_id))`: one row per person on an event's list, both ids cascade; `items` holds the extra items they left ticked; a row exists only while the attendance tick stands. `consent_log` gains nullable `wording` and `version` (the words shown and their version) for the scopes `event_attendance:<event>`, `event_share_email:<event>` and `event_share_card:<event>`. Rows go on an untick, when the host switches the list off, on account deletion, 12 months after the event ends (daily purge) and in the host reset. [[D038 Named attendance is per event, shown on the check-in page and pre-ticked by the owner's choice]].
- **Drops (F32, migration 0029, [[D039 Drops are sealed with a Worker key, given by one conditional write, and vouchers are marked with a staff PIN]]).** `drops` (event_id cascade; `kind` same, one_each, random or voucher; title, note, `reuse`, `per_person`, `valid_from`/`valid_until`, `status` on or stopped, `pin_mac` (voucher: an HMAC of the staff PIN, never the PIN), `check_cipher` (a sealed phrase that proves the key before an item is given), `purged_at` and `final_loaded`/`final_given`/`final_used` once cleared). `drop_items` (drop_id cascade, `seq` = its place in the host's list, `cipher` = `v1.` + base64url of IV, AES-GCM ciphertext and tag, sealed with the Worker secret `DROP_KEY`; empty once withdrawn; the database never holds an item in the clear). `drop_gives` (one row per person per drop, unique; a partial unique index on `item_id` where `exclusive = 1` so an item that goes to one person goes to one; `revoked_at`; an opaque `id` the host's named view uses to withdraw; a trigger deletes an exclusive item when its give row goes, so a deleted account never frees a key to be given again). `voucher_uses` (primary key drop, person, use number; `used_at`). `drop_audit` (what a host did: download, delete, withdraw, new PIN; counts and no values; 12 months). Given items, unused lists and voucher uses are deleted 30 days after the event ends (proposed); the F10 reset wipes all five tables. F34 (migration 0030, additive): `drop_gives.replaced_at`, set when a host replaces a person's item; the give row then points at the new item and the old one is wiped. A `replace` audit action in `drop_audit` (count 1, no value, no name).
- Nothing is stored for the Events tab or the event hub (F15, no migration): the list and the hub read `checkins`, `events` and `connections` and work out upcoming, ongoing or ended on each request with `worker/eventstatus.js`. `connections.event_id` may point at an event that no longer exists (F10 reset); the hub then returns 404 and the list leaves it out
- `host_accounts` (email UNIQUE lower-case, email_verified_at, full_name, use_case, event_frequency, typical_size, referral, terms_version, terms_at, status active|disabled, created_at, last_login_at, deleted_at): host accounts, separate from `users` (F10, migration 0018)
- `host_sessions` (SHA-256 of the cookie token, host_account_id, expiry, user agent), `host_login_codes` (email, hashed code, attempts, expiry, used_at)
- `orgs` (plan, org_type society|institution|company|individual, verification_status, leader, university, **institution_id** (F12, as on `profiles`), review notes)
- `host_org_members` (owner|staff|sponsor_viewer), `host_org_transfers`, `host_org_invites` (optional email), `host_org_tickets`: all on host accounts. `host_mail_log`: the owner recap, once per event
- Old, before F10: `host_profiles`, `org_members`, `org_transfers`, `org_invites`, `host_tickets` point at `users`. No code reads them; the host reset empties them and a later migration can drop them
- `events` (code, name, starts_at, venue, theme, strap_color, perks, directory_on, checkin_questions, is_paid)
- `checkins` (answers JSON, sponsor opt-ins)
- `sponsors`
- `credits` (events_granted, events_used, expires_at, reason, granted_by), `promo_redemptions`
- `billing_requests` (org_id nullable, org_name kept on the row, host_account_id, user_id before F10, sku, quantity, amount_pence, po_number, status open|invoiced|paid|cancelled). Since 0018 deleting an organisation sets org_id to NULL instead of deleting the invoice record
- **Host promo codes (F20, migration 0025).** `promo_codes` gains `audience` (`user` default | `host`), `credits`, `credit_days`, `org_kinds` (JSON list or NULL). A host code has reward `credits`, always a limit (`max_uses`), and its days in `days` too. `host_promo_claims` (claim_id, code, org_id (NULL if the organisation is deleted), host_account_id, position, credits, credit_days, credit_id (NULL while held), created_at, granted_at): unique on (code, org_id) and on (code, host_account_id), so a code is used once per organisation and once per host account. The credits row it issues has id `promo_<CODE>_<org id>`, reason `promo:<CODE>`, granted_by `promo`. The host reset wipes the claims with the organisations and sets host codes' `uses` back to 0. See [[D031 Host promo codes are one table, one claim per organisation and one generic refusal]]
- `plus_waitlist`
- **AI foundation (F21, migration 0024).** `ai_usage` (day UTC, actor_kind `user`|`host`|`admin`, actor_id, feature, scope (an event id for per-event limits), calls, input_tokens, output_tokens, cost_micros, cache_hits, fallbacks, limited): counts only, no text, kept 13 months. `ai_cache` (key SHA-256, feature, actor_kind, actor_id, result, created_at, expires_at): the checked reply, 7 days at most, the only generated text stored; never holds a prompt. `ai_daily` (day, cost_micros, calls, cache_hits, fallbacks, alerted): the whole app's spend. `ai_settings` (key, value): `killed`, `rollout` (`allowlist`|`plus`|`everyone`), `allow` (a JSON list of email addresses). `actor_id` has no foreign key (it can be a user or a host account); the purge and erasure remove orphans. See [[D028 AI goes through one Worker-side foundation that fails closed]]
- **Follow-up draft counts (F22, migration 0026).** `followup_counts(day UTC, kind, n, PRIMARY KEY (day, kind))`: `drafted_ai`, `drafted_template`, `copied`, `opened`, `marked`. No person, connection, event or text, so it is not in any export and nothing erases it; the daily purge removes rows after 13 months. Hosts never read it.
- **Feedback summaries (F23, migration 0027).** `feedback_summaries(event_id PRIMARY KEY, result, source, answers, created_at, auto_tries, auto_at)`, one row per event, `ON DELETE CASCADE`. `result` is the checked summary as JSON (paragraph; worked and change as `{ text, count }`; quotes as `{ text, question }`), `source` is `auto` or `manual`, `answers` is how many written answers it used (to say when newer ones have arrived). A row with `result` NULL only records that the automatic run tried (`auto_tries` stops at 3, `auto_at` the last attempt). It holds no name, no account and no text that is not an exact quote, and is the only copy of the generated text (not in `ai_cache`). Removed with the event, by the 12-month purge of written answers, and by the host reset. See [[D033 Feedback summaries count in code, quote exactly and never name anyone]]
- **People search (F24, no migration).** Nothing new is stored. A checked reply (opaque ids, a quote and a reason, no real id) is kept in `ai_cache` for 10 minutes, under the asker, with the people it was made from in its key, so it can never be served for a different set of people. All kept search replies are deleted at once when anyone opts out of AI search, blocks someone or deletes their account. It is in the asker's data download with the rest of `ai_cache`.
- **AI who to meet (F25, no migration).** Nothing new is stored. A checked reply (opaque ids, a quote and a reason) is kept in `ai_cache` for 10 minutes under the asker, with the people and everything sent about them in its key. All kept `who_to_meet` and people-search replies are deleted when someone withdraws or turns off event presence (including the 48-hour purge), opts out of AI search, blocks someone, or deletes their account. Usage is counted in `ai_usage` with `scope` = the event id.
- `feedback_responses`, `feedback_done`
- `org_integrations` (webhook url/secret, API key)
- `broadcasts`, `broadcast_sends`, `event_mail_log`

## Privacy by design
- Host reports are aggregate; named exports need per-sponsor opt-in. See [[Privacy and Data Retention]].
- Billing rows are kept when an org is erased (0018: `ON DELETE SET NULL`). Erasing an attendee no longer touches organisations (F10).
