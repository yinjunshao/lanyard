# Security

## Implemented (per code)
- Sessions stored hashed; HttpOnly cookies; SameSite Lax.
- Per-IP rate limits on new guests, wrong-code guesses, webhooks (`worker/ratelimit.js`).
- Passkey challenges held server-side (`webauthn_challenges`), single use.
- Managing passkeys (F43, [[D047 Passkeys are removed by one conditional delete that keeps a way to sign in]]): list, rename and remove are signed-in only (401 with no guest made), CSRF-checked like other writes, and scoped to the caller's own rows in the SQL (`user_id = ?`), so another person's id is a 404 with the same words as a made-up one. The list never carries the public key, counter or credential id. Removing the last way to sign in is a 409 decided inside one `DELETE`. Names are plain text. Tested in `test/passkeys-manage.mjs`.
- Private media: selfies served only to people in the connection.
- TOTP secrets encrypted at rest.
- Webhooks: https only, no IP literals or internal hostnames, no redirects followed, HMAC-SHA256 signature `Lanyard-Signature: t=...,v1=...`, 5 s timeout.
- Host API keys prefixed `lyk_`, webhook secrets `whsec_`.
- Security headers on every response (`worker/security.js`): CSP (self only, no framing), nosniff, Referrer-Policy, Permissions-Policy (camera self), HSTS on https, X-Frame-Options DENY, API responses `no-store`.
- Search and link previews (F37, [[D042 A shared card link shows what the card already shows, and is never indexed]]): `X-Robots-Tag: noindex, nofollow` on everything but `/`, `/hosts`, `/terms`, `/privacy`, `robots.txt` and `sitemap.xml` of the main site (the host site is all noindex); a card's preview is read in one query and shows only the profile name, the card's headline and a valid avatar key; a made-up, deleted or erased card gives the same page; an event preview counts wrong codes on the same counter as the API (F35.4); values go in through `HTMLRewriter`'s escaping `setAttribute`/`setInnerContent` only, with control characters removed, angle brackets replaced and lengths capped; the CSP and every other header are set after the rewrite, as before, and the shell's ETag and a browser's `If-None-Match` are not passed, so a card never answers 304 from an old copy.
- Same-origin check on all state-changing `/api` calls (CSRF defence on top of SameSite=Lax). The attendee API does not accept the host portal's origin.
- Host portal (F10): separate host-only cookie `__Host-lanyard_host` (SameSite=Strict), host API only on the host site and only from its own pages (Origin and Sec-Fetch-Site on reads and writes), email codes hashed with limits per email, per IP and per code, and replies that never reveal whether an account exists. Tested in `test/hostsecurity.mjs`. See [[Auth and Sessions]].
- AI (F21, [[D028 AI goes through one Worker-side foundation that fails closed]]): the key is a Worker secret read only by `worker/ai/client.js`, never returned, stored or logged; guests and signed-out callers are refused; per-person quota, burst and address limits, daily and monthly budgets, a kill switch and a timeout each fall back with a friendly message and cost nothing; the cache is keyed per person; data is delimited and escaped, replies are rebuilt from a schema; admin AI routes sit behind `ADMIN_TOKEN`; AI is off in production config and the local-only stub is refused off a local origin. Tested in `test/ai.mjs` and `test/ai-injection.mjs`.
- Follow-up drafts (F22): the model's input is read from the database for a connection the asker is in (the other person's card as shared with them, never their email, links, headline or hidden fields), the browser can only pick from what was offered, the request is inspected in tests, the reply is cleaned of links, emails, phone numbers and markup and cut to length, and nothing is sent by Lanyard. Attack cases: `test/ai-injection.mjs`. [[D032 Follow-up drafts are built from database rows and checked on the way out]]
- AI feedback summaries (F23): host routes behind the existing host guards (host site only, host cookie only, setup finished, the event's own organisation, 404 otherwise). The threshold of 5 written answers to one question is enforced in code before any model call. Attendees' words reach the model only after cleaning and redaction (names of the people at the event and the organisers, titles, phone numbers, handles), as data inside one `<data>` block; the reply is rebuilt from the schema, every sentence checked (no digits, number or count words, single-person phrases or names), counts worked out from the answer ids the model cites (different people, at least 3), quotes exact and from a well-answered question only. Plain text on the page, never HTML. What code cannot catch is a free sentence of the model's that is only words; the host reads it beside the real figures and the answers, labelled as written by AI.
- People search (F24): who is searched is decided in code before the model (own connections only; `blockedSet` and `searchableIds`; the card each person shared with the asker, read through the same card rule as `sharedCard`). The model sees opaque ids and cleaned, capped fields. Its reply is trusted only as far as it can be proved: an offered id, and a quote that is really in that person's record (a match with no such quote is dropped; a reply of invented matches falls back to keywords); a reason that names a number, an acronym, a capitalised word or an id that is not in the record is replaced by the quote. The asker's question is cleaned and goes in as data. Tested in `test/people-search.mjs` and `test/ai-injection.mjs`.
- AI who to meet (F25): the pool is `presenceCandidates()`, the same rows the usual list can show, gathered in code on every request; the model only re-orders it and the answer is rebuilt from rows gathered on that request, so a cached reply can never name someone who has left, been blocked or turned presence off. Opted-out people (`searchableIds`) are not sent and stay in the usual order after the picks. The model sees opaque ids and cleaned, capped fields; a field that reads like an instruction is left out (`looksLikeInstruction`); a pick stands only with a quote really in that person's record (F24's `verifyMatches`). The wish is read from the database, never from the request. The route refuses outside the event's live window before the cache is read, and the kept replies are deleted on withdrawal, block and erasure.
- Drops (F32, [[D039 Drops are sealed with a Worker key, given by one conditional write, and vouchers are marked with a staff PIN]]): pasted items (API keys, codes, passwords) are sealed with AES-256-GCM before they are stored, a random IV each, the key derived from the Worker secret `DROP_KEY` and the drop and item ids bound in, so a database copy alone reads as noise. No `DROP_KEY` (or one under 16 characters) means nothing is stored and the host gets one plain 503; a wrong key opens nothing and uses nothing up (a sealed check phrase is opened first). **`DROP_KEY` owner steps:** generate a long random value (for example 48 random bytes, base64), `wrangler secret put DROP_KEY`, keep a copy in the password manager; changing it later makes stored items unreadable, so unused lists must be loaded again and voucher PINs replaced. A host never reads an item back except the unused ones, by download (host site, own organisation, 5 an hour per drop, one audit row with a count and no values); a given item is never returned to a host, and names appear only through F31's list. An item and a voucher use are each one conditional write with a unique constraint behind it. Responses, errors, logs and exports are searched for every item and PIN in `test/drops.mjs`. Not covered: someone with the database, the Worker's secrets and a host's cookie together; a staff PIN seen over a shoulder (replace it, and it only ever marks the holder's own voucher).

- Limits and claims (F35, [[D040 Limits and claims are enforced in the write itself, and a guess is counted before it is checked]]): anything limited or handed out is one conditional write (event credits and a society's free week, the Free card limit, team invites, promo codes, drops, vouchers, note tokens); every wrong-guess limit takes its place atomically before the guess is checked (email codes 5 tries per code and 10 per address, the authenticator 10 per account, link codes, recovery keys and card codes 10 per IP, event join codes 30 per IP, all per 10 minutes) and hands it back on a right guess. Emails one person can make Lanyard send to another are limited per sender and per address (team invites, hand-overs, privacy acknowledgements). Numbers from the browser that are not whole numbers in range are a 400. Tested with requests sent at once in `test/security-audit.mjs`.

- Card payments (F36, off until `BILLING_ENABLED = "1"`): prices only from the server's table, paid only on a Standard Webhooks signature checked over every byte within 5 minutes, each `webhook-id` stored once and every grant in the same batch gated on it, refunds only from Polar, Polar secrets Worker-only; `test/billing.mjs` ([[D041 Polar as merchant of record behind one provider module]]).
- Company branding (F66, [[D061 Host branding shows on paid events only, keeps a Check in with Lanyard line, and takes PNG, JPEG or WebP logos up to 1 MB]]): a logo is PNG, JPEG or WebP by its magic bytes and must match the declared type (an SVG, a GIF, HTML or `<svg` declared as PNG, and PNG bytes declared as anything else are 400), at most 1 MB and 1024 px (read from the header), with text and metadata chunks removed; stored under `logo/<org id>/`; served with its own type, `nosniff`, a sandbox CSP, `same-origin` resource policy and no `Content-Disposition`; public only while a paid, branded event shows it, otherwise only to the organisation's own hosts, and any other key is a 404. Only the owner changes branding (staff 403, another organisation 404, signed out 401, an attendee cookie 401 on the host site). The display name is cleaned of control, zero-width and direction characters and drawn as text everywhere. Old logos are queued by database triggers and deleted from R2 on replace, remove and organisation deletion. An admin can remove a logo and switch branding off (audit-logged); the admin routes keep the token check (401 without it). Tested in `test/host-branding.mjs`.

## History
`test/baseline-security.txt` records an early snapshot where many checks FAILED (headers, CSRF, media access, challenge reuse); it is the **before** state. On 2026-11-15 (F35) `npm run test:security` passed 99 of 99, and the full `npm test` passed. The F35 audit checked the owner's 16 common attacks one by one: [[Security Audit 2026-11-15]] has the verdicts, the live read-only checks, what was fixed (2 High, 4 Medium, a few Low) and the owner steps, including how to rotate each secret.
