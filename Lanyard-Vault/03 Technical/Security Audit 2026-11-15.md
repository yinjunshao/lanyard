# Security Audit 2026-11-15

The owner's list of 16 common attacks ([[F35 Security audit against common attacks]]), each checked against the code as it stands on `main` at `4ebdf6e`, tried against the Worker in the offline tests, and, where it is safe and read-only, against the live site. Done by a Claude subagent. Severity: **High** = someone can read or change another person's data, get admin, get paid things free, or take a secret; **Medium** = abuse that costs money or floods email, or an injection that needs an unlikely step; **Low** = hardening.

**How races were tried.** The offline tests run the real Worker on an in-memory database that answers at once, so a request that has read its body used to run to the end before the next one moved. That hid check-then-write races. `test/security-audit.mjs` gives every single query one turn of the event loop (as real D1 does over the network) while a batch still runs alone as one transaction, then sends 10 to 50 requests at once with `Promise.all`. Every gap below was first shown failing that way.

Host details, Terms and organisation creation set only their own fields; `verification_status` comes from the kind (`hosts.js` `POST /api/host/orgs`), credits only from `insertEvent`, the promo code flow or an admin. The Plus price is the server's `PLUS_PRICE`. Proved in "Row 7". The rule for F27 and F36 is the payment bar in [[F27 Lanyard Plus and billing]]. |

| 9 | Click redeem 100 times at once | **Gap, fixed** | **High** | **Event credits** (`hosts.js` `insertEvent`): the credit check ran before the write and the event insert did not depend on it, so 20 Create presses at once with 1 credit left made 20 events and spent 1 credit; a society's one free event a week became 10. Fixed in F35.2: the event row is inserted only if a credit (or the free week) is still there inside the same transaction, and the credit is spent only if that row went in. Also fixed (F35.5): **team invites** (6 people joining with one invite code at once all joined), **the Free card limit** (10 cards at once gave a Free account 11 cards, a Plus feature). Already safe and now proved at once: the Plus poster code (60 people at once, 50 get it), host promo codes (`test/promo-host.mjs`), drops and vouchers (`test/drops.mjs`), note tokens (single `UPDATE ... WHERE redeemed_at IS NULL`). |
| 10 | Order -1 items and get a refund | **Gap, fixed** | Low | No refunds exist and prices are the server's, so no money moved; but numbers from the browser were bent instead of refused: an invoice request's quantity was clamped (`-1`, `0`, `1.5`, `"2"`, `[2]`, `true` became 1 or 2 and the request was saved), an RSVP count of `-1` became empty, and a feedback rating of `9` was quietly dropped. Fixed in F35.7: each is 400 and nothing is saved. Already strict: the RSVP API count, onboarding step, voucher uses, follow-up date, promo limits. |
| 11 | Brute force a 6-digit login code | **Gap, fixed** | **High** | The try was checked before it was counted, so guesses sent together all got through: 29 wrong attendee email codes and the right one, sent at once, signed in (limit 5 per code); 39 wrong authenticator codes and the right one signed in (limit 10 per account). The same check-then-count throttle guarded the sign-in link code, the recovery key and the card code lookup. Fixed in F35.3: an email code's try is taken by one conditional `UPDATE` before the code is compared, and every wrong-guess limit (per IP, per email, per account) takes its count first and gives it back only on a right guess. The host email code was already held to about 5 tries by its conditional `used_at` write (proved at once); it now takes its try first like the others. Signed-out card code lookups also shared one counter for everybody, so ten wrong guesses by anyone locked every signed-out visitor out for ten minutes; signed out, the IP is now the only counter. Expiry and single use were already right. |

Presence selfies also have their metadata stripped. Proved in "Row 12". Hardening (F35.7): profile photo changes were unlimited (each a storage write); now 20 an hour. |

| 14 | Call the AI endpoint 10,000 times | **Safe for AI; gap for email** | **Medium** | AI: per-person daily and monthly quotas, a 5-second burst limit, per-address limits, daily and monthly budgets and a kill switch, all before any call (`worker/ai/client.js`, `test/ai.mjs`). Sign-in codes were already limited per email and per IP. **Gap:** team invites could be sent to any address without end (invite, cancel, invite again: 25 emails in 25 tries), ownership transfer emails had no limit, and the privacy-request acknowledgement had a limit per IP only (20 IPs sent 20 emails to one address). | 15 | Query the whole database from the browser console | **Safe; one gap** | **Medium** | No route takes SQL or a table name; the D1 binding never leaves the Worker; responses are built field by field (no hidden column such as an email or a hash goes to another person; `test/security.mjs` checks the export). Lists return only the caller's own rows. | 16 | Secrets in general | **Safe; Low notes** | Low | `ADMIN_TOKEN`, `TOTP_KEY`, `DROP_KEY`, `RESEND_ACCOUNTS_KEY`, `RESEND_DECISIONS_KEY`, `CLAUDE_API_KEY` (and `UNSUB_SECRET` if set) are read only from `env` in the Worker; none is in `[vars]` of either `wrangler*.toml` (source guard); none is returned, logged or exported (errors are generic; `test/drops.mjs` and `test/ai.mjs` search responses and logs). ## Live read-only checks (2026-11-15, 31 GET or HEAD requests in all, none repeated)
- `HEAD https://lanyd.fyi/` and `https://host.lanyd.fyi/`: CSP as in `security.js` with `upgrade-insecure-requests`, HSTS one year, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `COOP same-origin`, `X-Robots-Tag: noindex`.
- `/.env`, `/.git/config`, `/wrangler.toml`, `/wrangler.production.toml`, `/.dev.vars`, `/.dev.vars.example`, `/migrations/0001_init.sql`: plain 404 on the main site; `/.env` 404 on the host site. `/package.json`: the app shell (no file).
- `/admin`: the app shell only. `/api/admin/queue`, `/api/admin/ai` signed out: 401. On the host site `/api/admin/queue` and `/api/me`: 401 `wrong_site`; `/api/host/me`: 401 `signed_out`.
- `/api/me` signed out: no user, the public plan list and prices only. `/api/connections` signed out: 401. `/api/health`: ok.
- The entry chunk and six page chunks downloaded and searched (row 4): no key, token or source map reference; `<entry>.js.map` answers the app shell, not a map.

## Not fixed (Low), for later
- A society's check-in limit (200) is counted before the check-in is written, so people checking in at the same moment can go a few over. No money; the cap is a fair-use line.
- The admin token is kept in the browser tab's `sessionStorage` on the main site. CSP stops inline script, so this needs a script-injection bug first; a separate admin origin would remove it.
- Attendee email codes are stored as SHA-256 of email and code without a pepper (host codes have one); a stolen database copy could test a live code within its 10 minutes.
- The data export, the host report and its CSV have no rate limit (each is one person's or one event's data, read only).
- Any unknown path that is not blocked (`*.map`, `*.json`) answers 200 with the app shell (`probes.js` blocks dotfiles and config extensions already).

## Owner steps
1. **Browser profile in git history (row 13).** As a precaution, change the passwords of the accounts saved in that browser profile if the GitHub repo is, or ever was, public or shared. To take the files out of history you would rewrite `main` (for example with `git filter-repo --path brag-output --path brag-output-2026-10-27-012233 --invert-paths`) and force-push; that changes every commit hash after 27 Oct, so it is your call. Also delete the local `backup/before-brag-removal-2026-11-13` branch and `refs/original/` when you no longer need them, and never push them.
2. Check whether the repo is public (`gh repo view --json visibility`, or the GitHub settings page).
3. Optional: set a separate `UNSUB_SECRET` (`wrangler secret put UNSUB_SECRET`) so the email-link key is not `TOTP_KEY`. Careful: this changes the signature of every unsubscribe link already sent (old "news" links stop working), so do it with a fresh mailing or not at all.
4. Optional: a Cloudflare WAF rate rule on `/api/*` POSTs per IP as an outer limit (the Worker's own limits stay the real ones).

## Rotating each secret
- `ADMIN_TOKEN`: `wrangler secret put ADMIN_TOKEN`; sign in again on `/admin`. If `TOTP_KEY` is not set it is also the fallback pepper for host codes (codes in flight stop working, 10 minutes) and the unsubscribe key.
- `TOTP_KEY`: changing it makes every authenticator setup unreadable (people set it up again), changes the host-code pepper (codes in flight stop) and, without `UNSUB_SECRET`, every email link.
- `DROP_KEY`: stored drop items become unreadable; load unused lists again and replace voucher PINs ([[D039 Drops are sealed with a Worker key, given by one conditional write, and vouchers are marked with a staff PIN]]).
- `RESEND_ACCOUNTS_KEY`, `RESEND_DECISIONS_KEY`: make a new key in Resend, `wrangler secret put`, then delete the old key in Resend.
- `CLAUDE_API_KEY`: new key in the Anthropic console with a spend limit, `wrangler secret put`, revoke the old one.
