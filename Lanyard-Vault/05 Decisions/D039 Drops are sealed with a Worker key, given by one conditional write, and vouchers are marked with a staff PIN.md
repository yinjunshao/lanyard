# D039 Drops are sealed with a Worker key, given by one conditional write, and vouchers are marked with a staff PIN

**Status:** Accepted  ·  **Date:** 2026-11-13

## Context
[[F32 Drops for codes, keys and vouchers]] lets a host hand out secrets (API keys, codes, Wi-Fi passwords) and food vouchers to people who checked in. The pasted items are secrets and a voucher is worth money, so a leak of the database, a host who is curious, two people pressing at once, and an attendee who wants a second lunch all have to be handled. Built on F10 as it stands. Owner decisions: hosts see counts only; they see names, and who got which item, only when the event has named attendance on and the person left the attendance tick on ([[D038 Named attendance is per event, shown on the check-in page and pre-ticked by the owner's choice]]).

## Decision
- **Sealed at rest, failing closed.** Every item is sealed with AES-256-GCM through Web Crypto: a random 96-bit IV per item, a key derived (HKDF-SHA-256) from the Worker secret `DROP_KEY`, and the drop id and item id bound in as additional data, so a ciphertext copied onto another row will not open. With no `DROP_KEY` (or one under 16 characters) nothing is sealed or stored and the host gets one plain 503; with a wrong or changed key an item will not open, nothing is returned and nothing is used up. This is the reverse of `TOTP_KEY`, which falls back to plain text. Errors, logs, host responses and the host export never carry an item.
- **Hosts see counts.** After the upload a host sees "120 loaded, 37 given, 83 left". The only way a host reads an item is to download the ones nobody has been given (POST, decrypted, host only, 5 an hour per drop, one audit row with the count and no values). A given item is never returned to a host. Names and which item went to whom (the item's number in the host's own list, never its value) come only through the named list rules of F31, checked on every request. Revoking is open only for someone on that list.
- **One conditional write gives an item.** A single `INSERT ... SELECT` writes the row only if the drop is on, inside its window, the person has nothing from it yet, and (for an item that goes to one person only) the item is free. Unique constraints are the second lock: one give per person per drop, and one give per exclusive item. A key given to a person is never given again, even if their account goes (a trigger deletes it with them). The write is proven with 51 people for 50 keys, twice-pressing and a crowd for the last items.
- **Vouchers are marked with a staff PIN.** The host is shown a six-digit PIN once, when the voucher is made (and again whenever they ask for a new one); the database keeps only an HMAC of it bound to the drop. Staff type the PIN on the holder's own phone, masked, and the voucher records one use with its time. The candidates were that, and a staff QR scan that opens a host-site page. The PIN won: it needs no staff accounts, no second device and no camera; the holder cannot mark their own voucher without it and a screenshot cannot either (the screen has a live clock, the holder's first name and photo); and what someone who learns the PIN can do is bounded, because the request comes from the holder's own session, so it can only ever mark the holder's own voucher, up to its count. The PIN is limited: five wrong tries per person per voucher in 10 minutes, then the person waits (even with the right PIN); a hundred wrong tries across everyone in an hour holds the voucher for all. A host can replace the PIN at any time. The risk left is a PIN seen over a staff member's shoulder: replace it, and it matters only for a person's own voucher. The scan stays an option if volunteers become a problem.
- **A use is one conditional write** too: the row is written only if the voucher is on and inside its window and the person has uses left, and the primary key (drop, person, use number) is the second lock. Two staff pressing at once record one use and the loser is told when it was used.
- **Eligibility.** Only a signed-in attendee who checked in to that event (a guest counts), while the drop is on and inside any window. Signed out 401, not checked in 403, another event's drop 404; the host site and host cookie get nothing. Drop routes never mint a guest account. A stopped drop gives nothing new and takes no voucher use, and people keep what they already have.
- **Retention (owner to confirm).** Given items, unused lists and voucher uses are deleted 30 days after the event ends (the same end rule as the event's status: the host's end, the end time, or 12 hours after the later of the start and the last check-in); the drop's title and its counts stay. An account's given items go with the account. The F10 reset script wipes everything.

## Consequences
A key that was leaked can be withdrawn only for a person the host can see (named attendance on, tick left on); otherwise the host deletes the drop and loads a new list. Changing `DROP_KEY` makes stored items unreadable, so unused lists must be loaded again and vouchers need a new PIN. Hosts who paste the same item twice get one: it is compared in memory, within the request, and never stored or returned. Revoking a given item withdraws it and gives that person no replacement.
