# D063 Admin-made profiles are private until claimed, by a hashed link and an emailed code, and deleted after 30 days

**Status:** Accepted  ·  **Date:** 2026-11-26  ·  Owner decision 2026-11-25 ([[F74 Admin-made profiles with a claim link]])

## Context
The owner wants to make a card for someone who is not on Lanyard yet, from details found elsewhere (for example LinkedIn), and send them a link to claim it. That card holds personal data about a person who has agreed to nothing, and the link is a new way into an account. The owner chose: **private until claimed** (only the link holder sees it), **deleted after 30 days unclaimed**, **claimed by confirming an email with a code**; and, for edits to existing accounts (F75), the person approves first.

## Decision
- **What it is.** An unclaimed admin-made account is `users.admin_made = 1 AND is_guest = 1` (migration 0046): a guest with a profile and one default card, no session, no email, no passkey and no way to sign in. `admin_made` stays 1 after the claim, for the record; `claimed_at` says when.
- **Private until claimed, everywhere.** `GET /api/c/:cardId` gives the same 404 body as a missing card to everyone (signed out, signed in, with the admin token). Its card code opens nothing (`findCardByCode`), its photo is not served at `/media` (only through the claim and admin routes, never cached), and its link preview is the made-up-card page (`seo.js`). `/api/connect` to it is the missing-card 404 and makes no guest. Two triggers refuse a `checkins` or `connections` row for it in the database, so it can never be checked in, connected or be connected, whatever route tries; every list that shows a person (People, people search, Who to meet, presence, the event room, host views and reports) reads those tables. The admin's account recovery search leaves it out and the admin cannot issue a sign-in code for it (409).
- **The link.** `/claim/p/<token>`: 32 random bytes (base64url, 43 characters). Only `SHA-256("claim-link:" + token)` is kept (`claim_links.token_hash`, unique), compared by hash. It ends 30 days after the account was made (Copy link never extends it). Copy link replaces the hash, so the old link stops at once; the admin sees a token once, in the answer that made it. The token travels only in the page address and in POST bodies: no admin route takes it, so it is never in `admin_audit` (which logs method, path and query); it is not in any email; rate-limit keys use a hash of it.
- **One plain answer.** A wrong, malformed, expired, replaced or used token all get `404 { error: "This link has expired or was already used.", code: "link_gone" }`.
- **Rate limits.** Every claim route takes a place on a per-IP and a per-token counter (`takeTry`, 10 per 10 minutes) before the token or code is checked (D040); a right one gives it back. Codes: 5 tries per code, the usual email limits (20 an hour per IP, 6 per address), and 5 codes an hour per link.
- **Claiming.** Start sends a 6-digit code (purpose `claim`) to whatever address is typed, account or not, so it never says which addresses have accounts. Finish needs the code and `acceptTerms: true, over18: true`, pressed under the line "By pressing Claim it, you confirm you're 18 or over and agree to the Terms and Privacy Policy." It is one batch gated on the link row: the `consents` row and the `consent_log` line (`notice:claim`, the words, the Terms version), the account made the claimer's (`is_guest = 0`, `email_verified = 1`, the email, 18+), and the link deleted. A second claim that runs after it changes nothing, so concurrent claims have one winner. Then the claimer gets a session (any other session in that browser is ended first) and lands on Edit profile with "Check your details". The admin never records consent for anyone: the admin routes do not touch `consents`, `consent_log` or `over_18`.
- **An email that already has an account** (verified or a legacy unverified sign-in address), checked only after the code proves the address: no merge, no sign-in, no session, nothing erased, the link keeps working, and the plain message. `handOffToExistingAccount` in `worker/claim.js` is the slot F75 fills (turn the details into a suggestion on that account, then erase the premade one).
- **Delete.** "This isn't me / delete it" erases the account and its photo with only the token, at once. The admin's Delete does the same. The photo key is queued in `media_deletes` first (F66), so a failed R2 delete is retried by the daily clean-up.
- **30 days.** The daily purge erases unclaimed admin-made accounts 30 days after they were made, with their photos; claimed ones are ordinary accounts and are never touched by it.
- **Same checks as Edit profile.** The admin routes use `worker/profileFields.js` (`profilePayload`, `validMode`, `applyInstitution`, `photoAllowed`), the code Edit profile and card making now import too, plus `readInstitution`. `source` (where the details came from) is required, one cleaned line of at most 80 characters, and is shown on the claim page (UK GDPR Article 14).
- **Metrics.** `METRICS_VERSION` 2: unclaimed admin-made accounts are left out of every count of people, profiles and cards, and counted on their own as `premade_waiting`.

## Consequences
The owner can make cards for people and send links, and nothing about those people is visible to anyone but the link holder; a person who says no is gone in one tap. The link is a bearer secret: whoever has it can see the card, delete it, or claim it with their own email, so the owner should send it only to the person (by a private message). The page address holds the token, so it can sit in the browser's history and is sent as the Referer on same-site requests (the Worker logs neither); a `#` fragment would avoid even that and is a possible later change. An email that already has an account gets nothing until F75 is built.
